## Title
Quest-Breaker: Narrative Deadlock & Inconsistency Engine for Branching Games

## The user and the problem
**User:** narrative designers and QA testers on branching RPGs and story games (Witcher / Baldur's Gate-style quest webs, visual novels, Ink/Yarn-based indie games).

**Problem:** a writer lets the player kill a character in Act 2, and a quest written months later in Act 5 assumes that character is alive. The player hits an impossible scene or gets soft-locked. Hundreds of quests branching on each other produce millions of playthroughs, too many to test by hand. Existing tools only check explicit flags or physics bugs. They cannot read the story text, where most of these contradictions actually live ("the jailer reports he died of fever"). Studios still track this in spreadsheets, and broken quests ship.

**Outcome:** upload the quest graph as JSON and get, in seconds, every deadlock with the exact failing playthrough. Example: "Aydan died in Step 2 'Silence the Minstrel', but Step 6 'Royal Wedding' has him perform". Each finding comes with an AI-written in-world fix. Adversarial player bots (Murder Hobo, Contrarian, Speedrunner) show which play styles get soft-locked.

## Disclosure
**Models:** `gpt-5.6-sol` via Azure AI Foundry (Azure OpenAI Responses API, structured outputs). It is used for the semantic contradiction check and the suggested story fixes. Optional: Claude (`claude-opus-5-5`) via the Anthropic API if an Anthropic key is configured. Development was assisted by an AI coding assistant (Claude Code).

**Data:** no external datasets. Three demo quest trees were hand-written during the hackathon. The evaluation benchmark is generated by our own script (`backend/benchmark.py`): quest graphs with labeled planted bugs and look-alike traps.

**Components:** Python, FastAPI, Uvicorn, Pydantic, NetworkX, OpenAI Python SDK, Anthropic Python SDK, pytest; React, Vite, Tailwind CSS, React Flow (@xyflow/react), lucide-react icons. All open-source libraries, used as published.

## Quality testing: what did you test, and what broke?
**Automated tests:** 55 pytest tests. They cover synthetic graphs with one known defect each (kill-then-require, a requirement that is only granted later, inescapable loops, orphan quests, a locked start), clean graphs that must produce zero findings (loops with exits, revived characters), archetype simulations, the API, and the scoring code.

**Comparison with the current approach:** we built a labeled benchmark and ran it on 16 held-out generated graphs. It contains 32 planted bugs: half encoded as state flags, half only in the story text. It also has 32 look-alike traps that are not bugs, such as a spared character, or a character who is needed before they are killed. Results:

| Approach | Precision | Recall | Flag bugs | Text-only bugs |
|---|---|---|---|---|
| Graph algorithm only (how flag checkers work today) | 100% | 50% | 100% | 0% |
| LLM only (whole graph in one prompt) | 96-100% | 62-72% | 25-44% | 100% |
| **Hybrid (Quest-Breaker)** | **100%** | **100%** | **100%** | **100%** |

The hybrid gave the same result on 2 repeated runs. Each approach alone catches about half the bugs; together they catch all of them. The graph algorithm enumerates every playthrough cheaply. The LLM reads only a small set of playthroughs that together cover every story branch: 3 calls per graph.

**What broke:**
1. The LLM caught a mistake in our own benchmark. A trap we labeled "safe" (buying a ship on an optional branch) really was a bug, because players who skip the branch later sail a ship they never bought. We fixed the label.
2. The first hybrid prompt raised 4 false alarms of the form "this character was never introduced before". We added the rule "a first appearance is not a contradiction". To avoid overfitting, we tuned on seeds 0-15 and report on unseen seeds 16-31.
3. The LLM-only baseline misses most flag-based bugs: it cannot reliably trace state across long branching paths.
4. Still missed: in the Witcher-style demo, a companion who was never recruited still raises a toast at the feast. The model judges this ambiguous.
5. Engineering bug: a cached async LLM client crashed across event loops. We now create one client per call.

**Limits:** the benchmark is synthetic and simple. Pre-conditions are equality checks only. Playthrough enumeration is capped at 500 paths.

## Feasibility (for the deck)
- **Data needed:** the quest graph the studio already has. Tools like articy:draft, Ink and Yarn Spinner export nodes, conditions and text, and a small converter maps them to our JSON.
- **Running cost:** the graph check is free and instant. The LLM pass used ~38K input / ~3K output tokens for 16 graphs (48 calls), roughly 2.4K input / 200 output tokens per playthrough checked. That is cents per full audit; run it on every script commit in CI.
- **Next step:** an Ink/Yarn importer, then a pilot on a real indie studio's script; numeric conditions (gold >= 50); a CI bot that comments on pull requests to the narrative repo.
